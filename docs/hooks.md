# Хуки в рабочем пространстве

`POST /hooks/{hookId}` запускает сохранённую задачу агента от имени владельца хука без открытого чата. Агент использует настройки, инструменты, скиллы и каналы владельца; промпт задаёт задачу и место доставки результата. Полезная нагрузка не получает отдельного ограничения прав: используйте доверенные события; изоляция полномочий хука описана в [#817](https://github.com/D00mch/souz/issues/817). Поддерживаются LOCAL и DOCKER, **один процесс backend**. Инструмента создания хуков и планировщика нет.

## Настройка и reload

Задайте `SOUZ_HOOK_OWNERS=user-42,user-43` или `souz.hooks.owners`. Пустой список отключает хуки. Пользователи должны существовать: YAML не создаёт учётные записи.

Создайте `<workspace>/hooks/<name>/hook.yaml`:

```yaml
version: 1
hookId: sample-123
ownerUserId: user-42
enabled: true
auth:
  type: bearer
  tokenSha256: "REPLACE_WITH_SHA256_OF_RANDOM_SECRET"
prompt: |
  Обработай событие и отправь результат в мой Telegram.
  Если канал недоступен, объясни это в результате выполнения.
```

Сгенерируйте секрет, например `openssl rand -hex 32`; в YAML храните только SHA-256. Bearer-токен содержит 32–512 символов без пробелов. Храните исходный токен в закрытой конфигурации клиента, вне Git, URL и промптов.

LOCAL читает общее настроенное workspace: файлы здесь — доверенная конфигурация оператора, без изоляции владельцев. DOCKER читает workspace соответствующего пользователя и требует совпадения `ownerUserId`. См. [контракт sandbox](../sharedLogic/docs/pain-points/runtime-sandbox-and-skills.md).

Читаются только `hooks/*/hook.yaml`. Неизвестные поля, небезопасные пути, некорректные хеши и сочетание `auth` с `verify` отклоняются. Некорректный файл отключает набор владельца; конфликт ID отключает все определения с этим ID. Диагностика не включает содержимое YAML.

Определения загружаются при запуске. `POST /v1/hooks/reload` через доверенный прокси перечитывает файлы владельца и возвращает `hookIds`. Смена токена, кода verifier и параметров применяется после reload. Удаление определения или `enabled: false` прекращает приём и обработку очереди. Изменение промпта или verifier отменяет ожидающие события предыдущей версии. Уже запущенную работу отменяют через API выполнения.

## Проверяющая команда

Вместо `auth` можно указать:

```yaml
verify:
  runtime: PYTHON
  script: scripts/verify.py
  parameters:
    audience: "https://your-host.example/hooks/sample-123"
```

Verifier запускается через `SandboxCommandExecutor` в LOCAL/DOCKER-среде владельца до создания квитанции, выбора Skill или обращения к LLM. Отдельный контейнер не создаётся. Это доверенный код с обычным доступом среды к файлам, сети и окружению; `python3` и библиотеки должны быть установлены в ней.

При загрузке сохраняется снимок каталога хука без `hook.yaml`: не более 64 файлов и каталогов, 1 МиБ суммарно, глубина до 8 компонентов. Симлинки запрещены. Относительные пути допускают буквы ASCII, цифры, `_`, `-`, `.`; компоненты `.` и `..` запрещены. `parameters` — JSON-объект до 8 КиБ.

Снимок копируется в `.hook-verifier-<uuid>` внутри workspace. Это рабочий каталог команды; после завершения или отмены он удаляется. Авария процесса backend может оставить каталог, но он не используется повторно. Постоянное состояние интеграции храните отдельно.

В stdin передаётся JSON:

```json
{"version":1,"method":"POST","path":"/hooks/sample-123","headers":{"authorization":["Bearer provider-token"]},"bodyBase64":"e30=","parameters":{"audience":"https://your-host.example/hooks/sample-123"},"checkedAt":"2026-09-24T18:00:00Z"}
```

`path` отражает путь после nginx; ожидаемый адрес берите из `parameters`. Заголовки приведены к нижнему регистру, значения сохранены списками; `Host`, `X-User-Id`, `X-Souz-Proxy-Auth` исключены. Допускается до 32 имён и 16 384 символов. Подпись проверяйте по исходным байтам `bodyBase64`.

Код завершения — `0`, stdout — ровно один JSON-объект:

```json
{"accept":false}
```

либо:

```json
{"accept":true,"eventId":"provider-event-123","payload":{"message":"new event"}}
```

При успехе обязателен `eventId`: 1–200 символов без управляющих, не пустой и не состоящий из пробелов. `payload` необязателен; без него исходное тело должно быть UTF-8 JSON. Лишние поля, дубли ключей и посторонний вывод отклоняются. Нормализованные данные остаются недоверенными; заголовки и параметры не передаются модели.

По умолчанию владелец имеет два общих слота приёма и проверки; reload не сбрасывает занятые слоты. Тайм-аут проверки — 5 секунд, stdout — до 64 КиБ. Используются механизмы отмены, завершения процессов и ограничения вывода sandbox. Отказ возвращает `401`; ошибка, тайм-аут или некорректный stdout — `503`. Stderr не включается в ответ и логи хука. Reload во время проверки делает её старый результат непригодным для приёма.

## HTTP и выполнение

Для Bearer-хука передайте `Content-Type: application/json`, `Authorization: Bearer <secret>` и JSON-тело до 64 КиБ. Необязательный `Idempotency-Key` имеет те же ограничения формы, что `eventId`. Для verifier допускаются произвольные исходные байты до 64 КиБ; ключ берётся из проверенного `eventId`, а `Idempotency-Key` игнорируется.

| Ответ | Значение |
|---|---|
| `202` | Квитанция записана в PostgreSQL; работа выполняется асинхронно |
| `200` | Повтор события: прежняя квитанция, без нового выполнения |
| `400`, `408`, `413` | Некорректный запрос, тайм-аут чтения, превышение размера |
| `401`, `404` | Отказ авторизации или недоступный ID |
| `409` | Ключ уже использован с другим телом или владельцем |
| `429` | Лимит приёма, проверок, очереди или событий за сутки |
| `503` | Хук отключён/изменён, хранилище или verifier недоступны |

Успешный ответ содержит `receiptId` и `duplicate`. Bearer проверяется до разбора тела; обе схемы авторизации работают до квитанции и LLM. Дедупликация сравнивает точный UTF-8 JSON: для Bearer — тело, для verifier — нормализованный `payload` либо исходное тело. Без ключа каждый Bearer-запрос создаёт событие. Ошибка выполнения не освобождает ключ.

`GET /v1/hooks/receipts/{receiptId}` через доверенный прокси возвращает владельцу статус, выполнение с `chatId`, итоговый текст, ошибку, число вызовов LLM и сообщённый расход токенов. Для событий, ответов на опции и отмены используйте существующие API выполнения. Успех агента сам по себе не подтверждает доставку сообщения: проверяйте результат инструмента отправки.

Каждое новое событие получает отдельный технический чат, скрытый из списка чатов. События одного хука последовательны; разные хуки разделяют лимит выполняющихся агентов. Ожидание опции освобождает слот, но удерживает очередь хука и бюджет события; продолжение снова занимает слот.

После перезапуска очередь продолжается, `waiting_option` сохраняется. Прерванная работа завершается ошибкой либо отменой с соответствующим долговечным событием. Завершённые состояния сохраняются, отсутствующие терминальные события восстанавливаются без дублей. Внешние эффекты с неизвестным результатом автоматически не повторяются.

## Лимиты и публикация

Значения заданы в [HookConfig](../backend/src/main/kotlin/ru/souz/backend/hooks/HookDefinitions.kt). Ограничены очередь, события владельца за сутки, параллелизм, длительность запуска, вызовы LLM на событие и владельца за сутки UTC. Попытки резервируются транзакционно **до** вызова, включая retries, вложенные инструменты и продолжения; перезапуск не сбрасывает бюджет. Дополнительно действуют минутные квоты запросов и сообщённых токенов, параллелизм провайдера и предел JSON-запроса к LLM. Ответ ограничивается 4096 токенами при поддержке провайдером; меньшие настройки summarization сохраняются. Это не фиксированный денежный потолок.

Маршрут ограничивает размер и время чтения тела, а параллелизм приёма и проверок — отдельно для каждого владельца. Bearer проверяется до занятия слота; медленный запрос одного владельца не занимает слоты другого. Ограничение частоты по IP настройте на ingress. Публикуйте через TLS. Для `/v1/hooks/**` сохраняйте обычную авторизацию прокси; для входящих хуков передавайте только авторизацию самого хука:

```nginx
location /hooks/ {
    auth_basic off;
    client_max_body_size 64k;
    client_body_timeout 5s;
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Authorization $http_authorization;
    proxy_set_header X-Souz-Proxy-Auth "";
    proxy_set_header X-User-Id "";
}
```

Для префикса `/souz` используйте `location /souz/hooks/` и `proxy_pass http://127.0.0.1:8080/hooks/;`.

## Проверка

`./gradlew :backend:test` требует Docker и локальный `python3`: проверяются рабочая сборка backend с PostgreSQL, авторизация, снимки verifier, дедупликация, доставка, очереди, бюджеты, опции и восстановление. Отдельные проверки протокола verifier и очистки процессов: `./gradlew :backend:test --tests 'ru.souz.backend.hooks.HookVerifierTest'`. Также выполните `./gradlew souzGateFast` и принятую проверку дублирования.
