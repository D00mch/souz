# Хуки в рабочем пространстве

Backend принимает `POST /hooks/{hookId}` с отдельным Bearer-токеном либо проверяющей командой самого хука. Успешный запрос ставит в очередь запуск агента от имени владельца хука. Открытый чат не требуется. Агент использует модель, инструменты, скиллы и каналы владельца; сохранённый промпт определяет задачу и место отправки результата.

Пилот рассчитан на **один процесс backend**. Поддерживаются рабочие пространства LOCAL и DOCKER. Инструмент создания хуков и встроенный планировщик не реализованы.

## Настройка

Задайте `SOUZ_HOOK_OWNERS=user-42,user-43` (или свойство `souz.hooks.owners`). По умолчанию список пуст и хуки отключены. В списке указываются существующие пользователи backend: до вызова хука пользователь должен войти через обычную доверенную точку входа. Чтение YAML не создаёт пользователей.

Создайте `<workspace>/hooks/<name>/hook.yaml`:

```yaml
version: 1
hookId: sample-123
ownerUserId: user-42
enabled: true
auth:
  type: bearer
  tokenSha256: "REPLACE_WITH_SHA256_OF_RANDOM_SECRET"
prompt: |
  Обработай событие. Сообщи о результате в мой Telegram.
  Если канал недоступен, сохрани понятное объяснение в результате выполнения.
```

Сгенерируйте случайный токен с энтропией не менее 32 байт, например командой `openssl rand -hex 32`. В YAML запишите его SHA-256 в шестнадцатеричном виде. HTTP-клиент хранит исходный токен в закрытом конфигурационном файле. Не помещайте токен в URL, промпт или логи. Допустимая длина Bearer-токена — 32–512 символов без пробельных символов.

Для ручного вызова удобно создать файл `hook.curl` с правами `600`:

```ini
url = "https://your-host.example/hooks/sample-123"
header = "Authorization: Bearer REPLACE_WITH_RANDOM_SECRET"
header = "Content-Type: application/json"
```

Если nginx публикует backend под префиксом, включите его в URL, например `/souz/hooks/sample-123`. Вызов:

```sh
curl --config /private/path/hook.curl \
  --silent --show-error --fail-with-body \
  -H 'Idempotency-Key: manual-check-001' \
  --data '{"event":"manual-check"}'
```

Повтор этой команды не запускает агента заново. Для нового события измените ключ. Конфигурацию с токеном храните вне Git.

LOCAL использует настроенное рабочее пространство runtime (по умолчанию — рабочую директорию backend). Файлы хуков здесь считаются доверенной конфигурацией оператора: общая файловая система LOCAL не обеспечивает изоляцию пользователей. Каждый владелец из YAML должен присутствовать в разрешённом списке на сервере. DOCKER использует рабочее пространство песочницы соответствующего пользователя и отклоняет YAML с другим владельцем. Контракт путей и исполнения описан в [документации runtime](../sharedLogic/docs/pain-points/runtime-sandbox-and-skills.md).

Загрузчик читает только `hooks/*/hook.yaml`. У определения должен быть ровно один способ авторизации: `auth` или `verify`. Неизвестные поля, некорректные хеши, небезопасные пути и повторяющиеся ID хуков отклоняются. Некорректный файл отключает весь набор хуков его владельца; в лог попадает диагностика без содержимого файла. ID должны быть уникальными на всём сервере: при конфликте недоступны все определения с этим ID.

Определения загружаются при запуске backend. Чтобы применить изменения без перезапуска, вызовите `POST /v1/hooks/reload` через доверенный прокси от имени владельца. Ответ содержит ID включённых хуков. Этот маршрут читает существующие файлы, но не создаёт их. Для смены токена замените `tokenSha256` и перезагрузите определения. Чтобы остановить приём новых событий и обработку очереди, удалите определение или задайте `enabled: false`, затем выполните перезагрузку. Изменение промпта отменяет обработку событий, ожидающих в очереди для его предыдущей версии. Уже запущенное выполнение отменяется через существующий API отмены выполнения.

## Проверяющая команда

Вместо `auth` укажите `verify`:

```yaml
version: 1
hookId: signed-event
ownerUserId: user-42
verify:
  runtime: PYTHON
  script: scripts/verify.py
  parameters:
    audience: "https://your-host.example/hooks/signed-event"
prompt: |
  Обработай проверенное событие и сообщи результат в мой Telegram.
```

Команда запускается напрямую через `SandboxCommandExecutor` в настроенной среде владельца хука: LOCAL или его DOCKER-песочнице. Новый контейнер для проверки не создаётся. Владелец определяется конфигурацией хука, а не запросом. Выбор скилла и обращение к LLM для проверки не нужны.

Скрипт выполняется с доступом к файлам, сети и окружению этой среды, как обычная пользовательская команда. Поэтому файлы хуков и скрипты считаются доверенной конфигурацией пользователя/оператора. Отдельных ограничений памяти, числа процессов или сети verifier не добавляет. `python3` и нужные библиотеки должны быть установлены в выбранной среде.

При старте/reload сохраняется снимок файлов каталога хука, кроме `hook.yaml`: до 64 файлов и каталогов, суммарно до 1 МиБ, глубина до 8 компонентов. Симлинки и выход из каталога запрещены. Пути относительные, их компоненты содержат только латинские буквы, цифры, `_`, `-` и `.`; компоненты `.` и `..` недопустимы. `parameters` — JSON-объект размером до 8 КиБ. Изменения кода и параметров применяются через reload и меняют revision хука.

Для каждого запуска снимок копируется во временный каталог `.hook-verifier-<uuid>` в workspace владельца; он же служит рабочим каталогом команды. Каталог удаляется после завершения, ошибки или отмены. После аварийного завершения самого backend могут остаться такие каталоги; они не используются повторно. Состояние интеграции храните отдельно, по постоянному пути, переданному в `parameters`.

В stdin скрипт получает один JSON-объект:

```json
{
  "version": 1,
  "method": "POST",
  "path": "/hooks/signed-event",
  "headers": {"authorization": ["Bearer <provider-token>"]},
  "bodyBase64": "e30=",
  "parameters": {"audience": "https://your-host.example/hooks/signed-event"},
  "checkedAt": "2026-09-24T18:00:00Z"
}
```

`path` — путь, полученный backend после преобразований nginx. Имена заголовков приведены к нижнему регистру, повторные значения сохранены списками. Не передаются `Host`, `X-User-Id` и `X-Souz-Proxy-Auth`. Всего допустимо до 32 имён и 16 384 символов заголовков. Для проверки подписи используйте исходные байты из `bodyBase64`; ожидаемый адрес/audience берите из сохранённых параметров.

Код завершения должен быть `0`, а stdout — ровно одним JSON-объектом:

```json
{"accept": false}
```

или

```json
{"accept": true, "eventId": "provider-event-123", "payload": {"message": "new event"}}
```

`eventId` обязателен при успехе: 1–200 символов без управляющих. `payload` необязателен; без него исходное тело должно быть корректным UTF-8 JSON. Дополнительные поля, дубли ключей и лишний вывод отклоняются. Нормализованные данные остаются недоверенными данными для агента. Заголовки и параметры проверки в промпт не добавляются.

По умолчанию одновременно выполняются не более двух проверок, тайм-аут команды — 5 секунд. Используются существующие механизмы тайм-аута, отмены и ограничения вывода sandbox. Stdout ограничен 64 КиБ; усечённый вывод не принимается. Stderr не включается в HTTP-ответ и логи хука. Отказ `accept:false` возвращает `401`; сбой запуска, тайм-аут, ненулевой код и некорректный stdout — `503`. Во время проверки можно отключить или перезагрузить хук: результат старого снимка не будет принят.

## HTTP-контракт

Для Bearer-хука передайте `Content-Type: application/json` и `Authorization: Bearer <secret>`. Тело — любое JSON-значение размером не более 64 КиБ. Хук с `verify` принимает исходные байты того же предельного размера; формат авторизации определяется его скриптом. Модели передаётся только JSON-событие после сохранённой задачи отдельным экранированным блоком с явной пометкой о недоверенных данных. Заголовки идентификации пользователя от прокси на этом маршруте не используются.

Для Bearer-хука необязательный `Idempotency-Key` (1–200 символов, без управляющих) обозначает повторные доставки одного события. Сравнивается точное тело запроса в UTF-8: изменение пробелов считается изменением содержимого. Для `verify` ключом служит обязательный `eventId` из результата скрипта; HTTP-заголовок `Idempotency-Key` игнорируется. Сравнивается JSON, передаваемый агенту: нормализованный `payload` скрипта либо исходное JSON-тело, если `payload` не задан.

| Ответ | Значение |
|---|---|
| `202` | Событие сохранено в PostgreSQL; агент выполнит задачу асинхронно |
| `200` | Событие с таким ключом и телом уже принято; возвращается прежняя квитанция |
| `400`, `408`, `413` | Некорректный JSON/ключ/тип содержимого, тайм-аут чтения тела, превышение размера |
| `401`, `404` | Некорректный Bearer-токен/отказ verifier или недоступный ID хука |
| `409` | Тот же ключ использован с другим телом или владельцем |
| `429` | Превышен лимит приёма запросов, параллельных проверок, очереди или событий за сутки |
| `503` | Хук отключён/изменён, хранилище или verifier недоступны, либо проверка завершилась технической ошибкой |

Оба успешных ответа содержат `receiptId` и `duplicate`. У Bearer-хука без ключа идемпотентности каждый запрос считается отдельным событием. Проверка Bearer выполняется до разбора тела. Проверяющая команда получает ограниченное исходное тело до его JSON-разбора. В обоих режимах создание квитанции и любые обращения к LLM происходят только после успешной авторизации.

Ошибка выполнения не освобождает ключ идемпотентности. Для намеренного повторного запуска используйте новый ключ, предварительно проверив, какие внешние действия успели выполниться.

Запросите `GET /v1/hooks/receipts/{receiptId}` через доверенный прокси от имени владельца. Ответ содержит статус, выполнение с внутренним `chatId`, итоговый результат, код ошибки, число зарезервированных обращений к LLM и расход токенов по отчётам провайдера. Каждое новое событие получает отдельный технический чат без истории предыдущих срабатываний. Повтор с тем же ключом возвращает существующую квитанцию и чат. С этим `chatId` работают существующие API событий чата, выбора вариантов и отмены выполнения. Технические чаты скрыты из обычного списка чатов и списка каналов; открыть их как публичные клиентские чаты нельзя.

Итоговый текст агента сам по себе не подтверждает отправку сообщения в канал: проверяйте результат инструмента доставки в событиях выполнения. Запасной получатель автоматически не выбирается. Статус `waiting_option` означает ожидание ответа пользователя и блокирует следующее событие этого хука до ответа или отмены.

## Выполнение и лимиты

Квитанция сохраняется до подтверждения приёма запроса. События одного хука выполняются последовательно; параллелизм между хуками ограничен. После перезапуска обработка очереди продолжается. Прерванные выполнения хуков завершаются ошибкой: внешние действия, которые могли уже выполниться, автоматически не повторяются. Восстановление хуков не изменяет обычные HTTP-, Telegram- и клиентские выполнения. Идемпотентность устраняет повторные HTTP-доставки, но не произвольные повторы действий агента.

Значения по умолчанию заданы в [HookConfig](../backend/src/main/kotlin/ru/souz/backend/hooks/HookDefinitions.kt). Ограничены размер очереди, приём событий за сутки, число параллельных выполнений, время одного запуска, число обращений к LLM на событие и на владельца за сутки UTC. Последние два счётчика резервируются **до** каждой попытки обращения к провайдеру, сохраняются при перезапуске и учитывают повторные попытки, вложенные вызовы из инструментов и продолжения после выбора варианта. Неудачные попытки и попытки с неизвестным исходом расходуют резерв. Полученный от провайдера отчёт о токенах добавляется к квитанции, даже если выполнение позднее завершится ошибкой.

К обращениям хуков к чат-модели также применяются квоты backend на частоту запросов, расход токенов и параллелизм у провайдера. Учёт подключён к hook-origin выполнениям, включая их вложенные обращения; минутные лимиты объединяют хуки одного пользователя. Обычные чаты через этот учёт не проходят. Размер JSON-запроса к LLM ограничен; запрашиваемый ответ ограничен 4096 токенами там, где провайдер поддерживает `maxTokens`. Эти ограничения не гарантируют фиксированного денежного потолка: различаются тарифы, reasoning-токены, генерация изображений, полнота отчётов о расходе и поддержка ограничения ответа. Квоты токенов опираются на сообщённый расход; жёсткий постоянный бюджет считает попытки. Достижение лимита завершает выполнение ошибкой без цикла повторных попыток.

Публичный маршрут имеет общие ограничения частоты и параллелизма запросов, а также тайм-аут чтения тела. Публикуйте его через TLS с отдельным блоком nginx для хуков; для `/v1/hooks/**` сохраняется обычная авторизация через прокси. Обработчик приёма хуков не записывает значения Authorization и тела событий в логи.

## Публикация через nginx

Добавьте в TLS server-блок отдельный маршрут. Он передаёт авторизацию самому хуку
и не подставляет доверенную личность пользователя. Для `/v1/hooks/**` сохраните
обычную авторизацию через прокси.

```nginx
location /hooks/ {
    auth_basic off;
    client_max_body_size 64k;
    client_body_timeout 5s;
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Authorization $http_authorization;
    proxy_set_header X-Souz-Proxy-Auth "";
    proxy_set_header X-User-Id "";
}
```

Если внешний адрес содержит префикс `/souz`, используйте `location /souz/hooks/`
и `proxy_pass http://127.0.0.1:8080/hooks/;`, чтобы backend получил `/hooks/...`.

## Проверка

Проверки verifier без Docker и PostgreSQL: `./gradlew :backend:test --tests 'ru.souz.backend.hooks.HookVerifierTest'`. Нужен локальный `python3`; запускаются настоящие процессы и проверяются снимок файлов, подпись, отказ, ошибки протокола, тайм-аут, отмена и лимит параллелизма.

Для изменений очереди и lifecycle запустите `./gradlew :backend:test` при доступном Docker. E2E-тесты хуков используют рабочую сборку зависимостей backend, PostgreSQL, настоящий граф выполнения и файловую систему; подменяются только ответы провайдеров и сети. При изменении исходников также выполните `./gradlew souzGateFast` и проверки дублирования, принятые в репозитории.
