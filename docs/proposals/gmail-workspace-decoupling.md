# Gmail: зависимости от workspace и варианты переделки

**Статус: предложение для ревью, не реализовано.** Код и контракт Gmail-плагина
сохранены. Workspace-методы SDK и их адаптер в backend остаются доступными,
поскольку Gmail вызывает их. Этот документ не утверждает, что перенос со старой
Python-интеграции нужен на конкретном стенде: наличие такого сценария подтверждено
кодом, наличие пользователей и данных для переноса ещё нужно выяснить.

## Проблема

JVM-плагин выполняется внутри backend и может хранить состояние в PostgreSQL,
а файлы — в S3. Два сценария Gmail обращаются к пользовательскому LOCAL/DOCKER
workspace через SDK. В DOCKER такое обращение может создать или запустить
пользовательский контейнер. Поэтому для этих сценариев ресурсные затраты включают
и прежний sandbox-механизм.

Общие изменения вне Gmail позволяют собирать inventory из существующих файлов
без запуска runtime и выбирать сохранённые S3-файлы для ответа без sandbox.
Они не устраняют описанные ниже вызовы из Gmail. Автоматические команды проверки
workspace-хуков и инструменты, принимающие workspace-пути, тоже могут запрашивать
sandbox независимо от Gmail.

## Скачивание вложения

Подтверждено [GmailContent.kt](../../plugins/gmail/src/main/kotlin/ru/souz/plugins/gmail/GmailContent.kt)
и [описанием команды](../../plugins/gmail/src/main/kotlin/ru/souz/plugins/gmail/GmailPlugin.kt):

1. `download_attachment(message, attachment, filename)` получает данные из Gmail API.
2. Проверяет размер, декодирует base64, проверяет фактический размер и сигнатуру PDF.
3. `files.saveWorkspace()` создаёт уникальный файл в пользовательском workspace.
4. Результат содержит `filePath`, исходное имя, размер, SHA-256 и признак недоверенных данных.
   Существующие инструменты чтения документов могут использовать путь.

Предлагаемое изменение:

- Сохранять байты через существующий `files.saveStored()` в пользовательское S3.
- Возвращать внутренний `fileId` и метаданные вместо `filePath`; не возвращать байты,
  base64, URL или путь backend.
- Сохранить проверки содержимого и владельца, обработку отмены и ошибок хранилища.
- Обновить инструкции команды и тесты на новый результат.

Это требует настроенного **пользовательского** S3-хранилища; бакет JAR-плагинов
не заменяет его. По [политике хранения](../../backend/docs/s3-storage.md) успешный
файл доступен 30 дней. Лимит Gmail — 25 МиБ, стандартный лимит S3 — 20 000 000 байт:
нужно явно согласовать их, чтобы переход не уменьшил допустимый размер незаметно.
Имя письма должно проходить политику имён хранилища и не становиться путём.

Скачать файл и прикрепить его к ответу можно через `fileId`. Сценарий «скачай PDF
и прочитай его» требует отдельной проверки потребителя: инструмент, принимающий
только workspace-путь, не начнёт принимать `fileId` автоматически. Копирование
S3-файла в workspace через `PrepareAttachment` сохранит зависимость от Docker.
Для выполнения целиком без пользовательского sandbox обработчик документа
должен получать байты из хранилища.

## Импорт подключения: что делает существующий код

`import_connection` — перенос настроек уведомлений и прогресса обработки почты
из файловой Python-интеграции. Это **не** авторизация Gmail и не обязательный
этап обычного поиска/чтения писем или создания новой настройки через `configure`.

Согласно [GmailFlow.kt](../../plugins/gmail/src/main/kotlin/ru/souz/plugins/gmail/GmailFlow.kt)
и [описанию workflow](../../plugins/gmail/docs/gmail-workflow.md):

- Вход: имя настройки `config` и абсолютный sandbox-путь `source` к `connection.json`.
- Плагин читает настройки из `connection.json` и, при наличии, состояние из соседнего
  `state.json` через `files.readWorkspaceText()`.
- Импорт сохраняет в PostgreSQL позицию обработки, пагинацию, дедупликацию,
  ожидающие сообщения, срок watch и признак разрыва истории.
- Незавершённые попытки доставки переводятся в неопределённое состояние и
  не повторяются автоматически. Существующее подключение не перезаписывается.
- Исходные файлы сохраняются; инструкция требует остановить прежний Python-hook
  и переключить hook-промпты на команды плагина.

`configure` не является эквивалентом такого переноса: новая настройка не сохраняет
прежний прогресс и очередь уведомлений. Удалять импорт как «ненужную совместимость»
без проверки реальных потребителей нельзя.

## Варианты импорта для решения на ревью

| Вариант | Что требуется | Последствия |
| --- | --- | --- |
| Читать экспортированные файлы из S3 | Загрузить `connection.json` и необязательный `state.json` в хранилище владельца; передать их ID | Меняется источник байтов. Можно сохранить существующую логику преобразования и проверки состояния. Появляется отдельный шаг экспорта/загрузки. |
| Вынести перенос в административную утилиту | Отдельный процесс читает старые данные и передаёт их через определённый контракт | В обычном плагине нет чтения workspace. Нужны владелец операции, контракт и способ безопасно остановить старую обработку. Прямой обход API записью в таблицы не предполагается. |
| Удалить перенос | Подтвердить отсутствие пользователей, которым нужны старые настройки и прогресс | Самый маленький контракт, но перенос состояния становится недоступен. Это продуктовое решение, а не техническое следствие перехода на JAR. |

Предварительное предложение при необходимости переноса — первый вариант:
`config`, `connectionFileId` и необязательный `stateFileId`; `files.loadStored()`
читает принадлежащие владельцу файлы, затем выполняется существующий импорт.
Имена параметров и выбор варианта **не утверждены**. Пока решение не принято,
команда и её текущее поведение сохраняются.

Вопросы для автора/ревьюера:

1. Есть ли реальные подключения Python-интеграции, которые предстоит переносить?
2. Кто и как сейчас запускает `import_connection`, откуда берутся исходные файлы?
3. Требуется ли перенос очереди и прогресса или допустима новая настройка уведомлений?
4. Если перенос нужен, кто выполняет экспорт и останавливает старый hook?

## Проверка после отдельного решения по Gmail

- Скачивание и прикрепление файла проходят без обращения к sandbox resolver;
  сохраняются проверки содержимого, владельца, размера и срока доступности.
- Вариант чтения документа проверяется сквозным сценарием, а не только сохранением в S3.
- Если импорт сохраняется, существующие проверки курсора, пагинации, watch,
  дедупликации, очереди, неопределённых доставок и отказа перезаписи остаются в силе.
- Если импорт удаляется, решение об отсутствии потребителей фиксируется явно.
- Удаление workspace-методов из SDK и адаптера выполняется согласованно
  с изменениями Gmail и примерных/тестовых плагинов внутри этого PR.
  Требований поддерживать опубликованные внешние JAR в текущем обсуждении нет.
