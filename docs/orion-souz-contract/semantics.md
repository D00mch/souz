# Orion-Souz Semantics

## Identity

Every `/v1/**` request and WebSocket upgrade uses trusted proxy headers:

- `X-Souz-Proxy-Auth` authenticates the trusted proxy boundary.
- `X-User-Id` is the authoritative Souz user ID.

For Orion traffic, `X-User-Id` is the normalized `SberID.UUID` after SberID token validation. Request bodies may include voice or device hints, but they are not authoritative identity.

Souz does not receive raw audio in this contract. Orion receives audio from the device, performs ASR and TTS, and sends recognized text to Souz.

## Sessions

`sessionId` is generated by Orion and is unique within a user. Repeating an open-session request with the same user and `sessionId` returns the same `chatId`.

`deviceId` is stable for the physical or logical device. `deviceType` describes the current channel capabilities, not the user.

## Message Idempotency

`requestId` identifies the user request observed by Orion. `clientMessageId` identifies the Souz message submission and is unique within `(userId, sessionId)`.

Repeating a message submission with the same `clientMessageId` and the same normalized payload returns the existing execution. Repeating it with a different normalized payload returns `409 idempotency_conflict`.

Normalized payload includes recognized text, `sessionId`, `requestId`, `deviceId`, `deviceType`, and request-scoped options that affect execution.

## Event Replay

Durable events have `durable = true` and a non-null `seq`. `seq` increases monotonically within `chatId`.

`afterSeq` is exclusive: the server sends durable events with `seq > afterSeq`.

On WebSocket connect, Souz sends the durable backlog first, then live events. Live-only events have `durable = false` and `seq = null`; they are not replayed after reconnect.

## Commands

Orion sends commands over the chat WebSocket when Souz needs a device-tool result, user option answer, or cancellation. Every command has a `commandId` unique within `(chatId, sessionId)`.

Souz acknowledges every accepted or rejected command with an `ack` frame. Souz stores the command acknowledgement result and repeats the same acknowledgement for duplicate `commandId`.

If a duplicate command has the same payload, the acknowledgement has `duplicate = true`. If the same `commandId` arrives with a different payload, Souz replies with `status = rejected` and `error.code = idempotency_conflict`.

## Terminal State

Each `executionId` has exactly one terminal durable event:

- `execution.finished`
- `execution.failed`
- `execution.cancelled`

If completion and cancellation race, the first persisted terminal state wins. Repeated cancellation returns the current execution state and does not create another terminal event.

## Device Tools

Souz emits `device.tool.requested` when the Agent Graph chooses a tool that must run on the Orion device. Orion runs the device action or asks the user for permission, then sends `device.tool.result`.

The `toolCallId` links request and result. Orion must return `status = failed` with a structured error when the device cannot complete the action before `deadlineAt`.

## User Options

Souz emits `option.requested` when the agent needs a user decision. Orion renders the choice or permission prompt and answers with `option.answer`.

The existing REST endpoint `POST /v1/options/{optionId}/answer` is the fallback path when WebSocket commands are not available.

## Errors

HTTP errors use the shared `ErrorEnvelope`. Command errors use the same `Error` shape inside `ack.error`.

All unknown enum values must be treated as non-terminal unless the specific field says otherwise.
