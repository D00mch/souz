# Client-Souz Semantics

## Identity And Client Profiles

The contract supports two public client profiles:

- `backend` is a server-to-server client profile. It uses `X-Souz-Proxy-Auth` and `X-User-Id`; `X-User-Id` is the authoritative Souz user ID.
- `mobile_app` is a direct mobile application profile. It uses the mobile app auth profile; Souz resolves the authoritative user from that token.

Client declares `clientType` when creating a chat and when opening `/v1/chats/{chatId}/ws`. `clientType` selects the authentication profile and client capability surface. It does not add a third tool execution target.

The WebSocket `clientType` must match the chat's stored `clientType` and the presented authentication profile. A mismatch is rejected before replay or live traffic starts.

Device metadata is not authoritative identity. Souz receives recognized text and its input `source`; raw audio and speaker identity stay on the Client side.

## Chat Lifecycle

Client generates a create-chat `requestId` before `POST /v1/chats` and stores it locally until chat creation succeeds. `POST /v1/chats` creates a user-owned chat for the declared `clientType` and returns its `chatId`. Client stores the `chatId` and uses `/v1/chats/{chatId}/ws?clientType=...` for further interaction.

A chat outlives WebSocket connections and threads. Reconnecting to the same chat does not create another chat or thread.

## Threads And Messages

A thread is a task inside a chat. It can contain multiple user submissions and tool calls. Completing a thread does not complete its chat.

Client sends the first `message.submit` with a Client-generated `requestId` and without `threadId`. Accepting it is one atomic operation: Souz persists the submission and creates its thread. The acknowledgement correlates the request with the thread:

- `requestId` equals the submitted `requestId`.
- `submission.inputSeq` is the thread-local input sequence assigned to the accepted user submission.
- `thread.created` is `true`.
- `thread.status` is `running`.
- `thread.revision` is the latest accepted input sequence for the thread.

Client includes the active `threadId` in a subsequent `message.submit`. Its acknowledgement contains the existing thread with `thread.created = false`.

Client may submit additional user messages to a running thread. Souz atomically appends every accepted submission to the thread input log. If an internal execution is already running, Souz may interrupt, supersede, or continue it internally, but this is not visible in the public contract. Publicly, the thread remains `running`.

An accepted submission is part of the same thread and must be observed by the agent before the thread reaches a terminal state.

An accepted acknowledgement means the submission and thread association are durable. It does not mean the thread is complete.

The acknowledgement is the first Souz frame caused by an accepted submission and precedes lifecycle events caused by that submission.

A separate `thread.started` event is not emitted because the accepted acknowledgement already communicates that state transition.

## Idempotency

Create-chat idempotency is scoped by `(userId, requestId)`. The normalized create-chat payload includes fields that affect the created chat, including `clientType` and `title`. The first accepted request returns `201 Created`, `duplicate = false`, and the created chat. Retrying the same `requestId` with the same normalized payload returns `200 OK`, `duplicate = true`, and the same chat. Reusing the same `requestId` with a different normalized payload returns `409 idempotency_conflict` and does not expose a usable `chatId`.

The create-chat `requestId` is independent from `message.submit.requestId`.

WebSocket `requestId` is generated by Client and is unique within the chat for `message.submit` and `thread.cancel`. It is independent from the create-chat `requestId`.

For `message.submit`, Souz stores the normalized payload, thread association, and acknowledgement by `(chatId, requestId)`. Repeating the same `requestId` and normalized payload returns the original acknowledgement with `duplicate = true`. Reusing the request ID with a different payload returns `status = rejected`, `thread = null`, and `error.code = idempotency_conflict`.

For accepted `message.submit`, `submission.inputSeq` increases by one within the thread. Retrying a duplicate `message.submit` returns the original `inputSeq` and `thread.revision`.

For `thread.cancel`, Souz stores the normalized payload and acknowledgement by `(chatId, requestId)`. The normalized payload includes `kind`, `threadId`, and `reason`. Repeating the same `requestId` and normalized payload returns the original acknowledgement with `duplicate = true`. Reusing the request ID with a different WebSocket message kind or payload returns `status = rejected` and `error.code = idempotency_conflict`.

`toolCallId` is generated by Souz and is unique within a thread. Client returns the same `toolCallId` in `tool.result`; a separate tool call receives a new ID. A tool accepts one terminal result, so result idempotency is scoped by `(chatId, threadId, toolCallId)`.

Accepting `tool.result` and storing the result is one atomic operation. Souz returns a `ToolResultAck` for accepted and rejected results. The normalized terminal-result payload includes `status` and exactly one of `result` or `error`; generated metadata such as `receivedAt` is not part of the normalized payload.

Repeating the same terminal result returns an accepted acknowledgement with `duplicate = true` and does not append another event. Reusing the same `(chatId, threadId, toolCallId)` with a different terminal payload returns `status = rejected`, `duplicate = false`, and `error.code = idempotency_conflict`.

## Event Replay

Every event has a `seq` that increases monotonically within `chatId`. `seq` identifies the event for ordering, replay, and deduplication; a separate `eventId` is not used.

`afterSeq` is exclusive and scoped to the chat identified by `/v1/chats/{chatId}/ws`. On WebSocket connect, Souz sends events with `seq > afterSeq` in order and then continues with live events. After replay catches up, Client sends new messages on the same connection using normal `requestId` and `toolCallId` idempotency.

Message-submission and thread-cancellation acknowledgements are stored by `(chatId, requestId)` and repeated when the corresponding Client message is retried. Tool-result acknowledgements are stored by `(chatId, threadId, toolCallId)` and are outside the event sequence.

## Terminal State

Each thread has exactly one terminal event:

- `thread.completed`
- `thread.failed`
- `thread.cancelled`

If completion and cancellation race, the first persisted terminal state wins. Cancellation after a terminal thread is acknowledged as an accepted no-op and does not create another terminal event.

If `message.submit` is committed before the terminal thread event, the terminal result must account for that submission. If the terminal thread event is committed first, the submission is rejected with `error.code = thread_already_terminal`.

## Tool Calls

Souz emits `tool.call.started` for every tool call in a thread. `target = souz` means the tool runs inside Souz. `target = client` means the connected Client side must perform a device action or collect user input and return `tool.result`. The connected Client side can be `backend` or `mobile_app` according to `clientType`.

For a Client-targeted tool call, `ToolResultAck` confirms that Souz accepted or rejected the result. A succeeded `tool.result` contains `result`; failed, cancelled, and timed-out results contain `error`. A thread may contain multiple tool calls before producing its final response.

## Errors

HTTP errors use the shared `ErrorEnvelope`. WebSocket acknowledgements use the same `Error` shape in `error`.

Unknown enum values must be treated as non-terminal unless the specific field says otherwise.
