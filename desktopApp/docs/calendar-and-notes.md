# Calendar and Notes

Data access must not open native app windows or move keyboard focus. Tool construction and DI registration perform no Calendar or Notes IO. Opening the default-calendar dropdown in Settings emits `FetchCalendars`; `SettingsViewModel` invokes the desktop `CalendarListProvider`, which runs `CalendarAppleScriptCommands.listCalendarsCommand`. Calendar create/delete/list tools execute native work only when invoked. Desktop indexing calls `DesktopDataExtractor.notes`, which skips stopped Notes.

Sending data events to a stopped scriptable application can invoke its normal startup behavior. Calendar data scripts and Notes create/list/search/delete scripts send `launch` before data events. Apple's [launch contract](https://developer.apple.com/library/archive/documentation/AppleScript/Conceptual/AppleScriptLangGuide/reference/ASLR_cmds.html) skips the normal `run` handler and is inert for a running app. A background app process may exist; data operations must not activate, reopen, show, or hide native windows. Notes creation is a data operation. `OpenNote` deliberately uses `activate` and `show`; the general `Open` tool sends registered bundle identifiers and `.app` paths to Launch Services for explicit app opening. `Open` checks dotted names against the Launch Services application registry without launching an app; unregistered names such as `Project v2.0` retain folder lookup. Registered application launch failures remain errors.

`CalendarListEvents` uses public EventKit through macOS JavaScript for Automation, with arguments passed separately from source. It queries local midnight to the following local midnight, including daylight-saving transitions. EventKit resolves overlapping events, recurring occurrences, and exceptions. No private Calendar or Notes databases are accessed. Calendar scripting preserves calendar selection, creation, reminders, and deletion semantics; Notes scripting preserves first-account creation and first-name-match deletion. Notes input is passed as literal arguments.

macOS Automation permission is required for Calendar and Notes scripting; event listing requires full Calendar access. EventKit requests full access on first invocation (including upgrading write-only access), with the legacy API on older macOS. The process has a deadline; denied/restricted access, unknown calendars, invalid dates, and native failures reach the caller as errors rather than empty results. Existing Souz tool-approval checks still gate note mutations. OS consent is separate from those checks. The first OS permission prompt is expected; granting permission must not open the target app's normal windows.

For a packaged macOS smoke check, use an isolated Souz home and an in-memory Java Preferences factory, a local deterministic provider fixture, and a macOS test profile containing only synthetic Calendar/Notes data. Do not inspect real accounts or reset OS permissions. Record the candidate path/revision and fixture, and mark each scenario passed, failed, or not run:

- Quit Calendar and Notes. Launch the packaged Souz app through LaunchServices, verify keyboard input, and check that neither native app has a window or takes focus. Constructing/enabling tools also leaves both apps closed.
- Open Settings' default-calendar dropdown. This exercises Calendar discovery without an agent invocation. Calendar may run in the background, but no window may open or take focus.
- With Calendar initially quit for each operation, list fixture calendars/events, create an event with location/description/reminder, list it, and delete it. Verify recurring, all-day, and overlapping fixture events. Confirm results and absence of unexpected windows/focus changes. Repeat while Calendar has an existing window; leave its focus and visibility unchanged.
- With Notes initially quit for each operation, create a uniquely named synthetic note, list/search it, and delete it. Verify returned results and absence of unexpected windows/focus changes. Repeat with an existing Notes window. Include quotes, backslashes, and multiline note text.
- In a profile with denied permissions, invoke each affected integration and verify a clear failure without false success or a native app window. A missing OS grant blocks the granted-permission checks; do not change permissions during automated validation.
- Explicitly invoke `OpenNote` for a synthetic note and `Open` for Calendar/Notes. Verify the requested app becomes visible and the note is selected; clean up only synthetic fixtures.

Regression tests compile data scripts against native scripting dictionaries without executing the apps, exercise the production EventKit script with synthetic stores, and verify launch/activation boundaries, permission failures, literal Notes input, and local-day bounds. They do not establish actual app window/focus behavior; that requires the packaged smoke check.
