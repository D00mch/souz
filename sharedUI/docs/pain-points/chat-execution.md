# Chat execution

`ChatUseCase` owns one request session from the first user message through the final assistant response. Active-run input belongs to that session; it must not call `sendChatMessage`, reset the agent, or create another observability request.

Accepted active-run input is shown as another user message. Its acceptance and UI bookkeeping share the active-request mutex with terminal response rendering, so an accepted continuation is committed before the final assistant message. The continuation's voice modality becomes the modality of the replacement assistant response for streaming and non-streaming speech. The provisional assistant message is removed and its streaming accumulator is reset before replacement output is rendered. Text side effects carry the producer's stream revision; the collector handles them under the same mutex and discards revisions older than the session instead of assigning ownership at collection time. Each request session retains the IDs of its original and continuation messages, so cancellation removes them together with the pending assistant message even after another input source supersedes the request.

The UI uses `AgentId` metadata to expose active-run input only while the selected agent supports it, a request is processing, and no tool review is awaiting a decision. Actual acceptance still requires the live mailbox retained by `AgentFacade`. Text input and voice capture started in that window target the active run; neither starts a new request. On-screen and global-hotkey voice capture are blocked while tool review is pending. Voice capture fixes its route when recording starts, and an active-run route carries the owning request ID. Active-run recognition bypasses voice review and submits immediately. Recognition is accepted only while that request ID owns the session. If completion, replacement, or rejection closes that route, the recognized text is retained as an ordinary editable draft and never falls through to a new request. Voice review applies only to captures routed to a new request; reviewed transcription remains editable until its send is accepted or the input is cleared.

Stop returns captured audio bytes directly, so recognition uses the same route without a separate audio-flow queue. Stop handling runs outside the serialized UI event collector, so a voice-started request cannot delay follow-up recording events until its assistant response completes. Voice capture and recognition status reducers do not own `isProcessing`, which belongs to the chat request session. Send and Stop remain separate actions. The ViewModel publishes accepted or rejected submission feedback; host UI clears the local draft only after acceptance and retains it after rejection.
