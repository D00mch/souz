# Chat execution

`ChatUseCase` owns one request session from the first user message through the final assistant response. Active-run input belongs to that session; it must not call `sendChatMessage`, reset the agent, or create another observability request.

Accepted active-run input is shown as another user message. Its acceptance and UI bookkeeping share the active-request mutex with terminal response rendering, so an accepted continuation is committed before the final assistant message. The continuation's voice modality becomes the modality of the replacement assistant response for streaming and non-streaming speech. The provisional assistant message is removed and its streaming accumulator is reset before replacement output is rendered. Text side effects carry the producer's stream revision; the collector handles them under the same mutex and discards revisions older than the session instead of assigning ownership at collection time. Each request session retains the IDs of its original and continuation messages, so cancellation removes them together with the pending assistant message even after another input source supersedes the request.

The UI exposes active-run input only while the selected agent supports it, a request is processing, and no tool review is awaiting a decision. Text input, the on-screen microphone, and automatically submitted voice recognition use the same continuation route; none starts a new request while an active run is open. On-screen and global-hotkey voice capture are blocked while tool review is pending. Voice capture fixes its route when recording starts, and an active-run route carries the owning request ID. Continuation capture does not abort the active request, and its recognized text is submitted only while that request ID still owns the session; completion, replacement, or rejection never falls through to another request. Reviewed voice drafts retain every recognized segment and their capture-scoped route until accepted submission or input clearing. Additional reviewed captures may join the draft only when their routes match; the ViewModel applies only segments newer than its last applied capture token, while a route change blocks recording until the current draft is sent or cleared. Recorder transitions remain serialized until asynchronous stop reaches a terminal state. Failed capture start or stop clears the pending route, a terminal capture with an unconsumed route clears that route, and audio collection remains active while recoverable recognition errors back off so a completed capture cannot lose its route. Audio without a route is ignored. Voice capture and recognition status reducers do not own `isProcessing`, which belongs to the chat request session. Send and Stop remain separate actions. The ViewModel publishes accepted or rejected submission feedback; Android and Desktop clear the local draft only after acceptance and retain it after rejection. A rejected submission does not fall through to a new request because the current run may be crossing its final-response boundary.
